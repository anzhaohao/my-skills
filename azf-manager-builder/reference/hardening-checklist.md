# 加固清单（12 条，全部来自 2026-09-22 的真实踩坑）

造/改管理器时逐条核对。每条都写清"坑长什么样"，因为漏掉任何一条都会在几天后以"莫名其妙不工作"的形式回来。

## 1. `.ps1` 必须 UTF-8 **带 BOM**

PowerShell 5.1 读无 BOM 的文件会按 ANSI 解码，中文注释与提示语变乱码，字符串引号会被吃掉 → 直接语法错误（本次实测：`Array index expression is missing or not valid`）。
编辑工具（含各类 AI 编辑器）写回时**会静默去掉 BOM**：每次改完 `.ps1` 都要复检首字节是否为 `EF BB BF`。

## 2. 退避计数在健康后必须归零

本次真 bug：`ConsecutiveFailures` 只加不减 → 重启几次就永久进入 300 秒退避档，表现为"管理器还在，但服务起不来了"。
正确做法：进程存活**且端口已监听**时把计数与下次重试时间清零。

## 3. 健康检查看端口，不只看进程

只有"进程还在"不算健康：进程可能卡死、端口没绑上、或绑在别的实例上。判定标准是**它该监听的端口在监听**；进程活着但端口没起超过阈值（如 20 秒）→ 重启。

## 4. 启动时清理孤儿端口 + 单实例互斥

强制结束管理器或系统重启后，子进程可能变成孤儿继续占端口，新实例就会绑不上。
启动顺序：命名互斥体抢单实例 → 扫出占用目标端口的 PID 并结束（排除自身 PID）→ 再启动子进程。

## 5. "无窗口"要实测，不能假设

编译加 `/target:winexe`、子进程 `CreateNoWindow=true`，然后**断言** `MainWindowHandle -eq 0`。本次验证方式：`(Get-Process <名字>).MainWindowHandle`。

## 6. 状态落盘 + 日志 + 托盘三件套

- `manager-status.json`：状态机、每个子进程的 pid/running/portsUp/starts/lastError、端口检查表、各钩子的执行统计；
- 日志：管理器自身日志 + 每个子进程的 stderr 落独立文件，带大小轮转；
- 托盘：绿=全部正常 / 黄=自愈中 / 红=未运行 / 灰=已暂停；状态跃迁时弹气泡提示；菜单含打开面板、打开日志目录、重启单个/全部、暂停自愈、退出。

## 7. 计划任务与回滚

登录触发 + 延迟约 20 秒 + 失败重启 3 次 × 1 分钟 + 执行时长不限（`ExecutionTimeLimit = PT0S`）。
**旧的启动方式（旧计划任务/旧脚本）停用但保留**，README 写清启用回去的命令——这是你的回滚底线。
principal 沿用本机既有任务的形态：`<用户名> / Interactive / Limited`。

## 8. 自愈钩子必须幂等，且不与其它写者打架

钩子只有两类：
- `file-prefix`：某文件必须保持某形态（例：Bearer 文件必须是 `Bearer <token>`）；内容是目标形态就**什么都不做**；
- `run-script`：按需运行维护脚本（例：模型目录补全）。

要点：只在内容**不符**时才改（否则会和其它写者形成写循环）；需要子进程重读文件时，才顶掉该进程让它被重新拉起；把每次执行记进状态文件。
本次反面教材：`models.json` 被两个写者反复覆盖，先解包才恢复。

## 9. 固定 CLI 契约，脚本优先调 CLI

`--status`（写一份状态并退出）、`--stop`（结束子进程）、`--restart <child|all>`（结束端口占用者，常驻实例会在数秒内拉起）、`--headless`（无托盘守护）、`--fix-*`（一次性执行某钩子）。
项目脚本里不要再操作计划任务——任务可能已停用，重启要靠管理器自己的能力。

## 10. 按命令行特征杀进程时排除自身 PID

本次真实事故：用 `CommandLine -match '<关键字>'` 杀进程，**匹配到了自己这条命令**（命令文本里就含那个关键字），把自己连带杀掉，后续步骤全没执行。
规则：过滤时永远加上 `-and $_.ProcessId -ne $PID`，并且关键字不要用自己命令行里出现的字面量。

## 11. 密钥只走环境变量或 `.env`

`manager.json` 里不写密钥；管理器启动子进程时从 `.env` 注入；日志脱敏（Bearer、Key、长 base64 打码）。
`.env` 进 `.gitignore`，仓库里只留 `.env.example`。

## 12. 每次改动后跑真实演练，并把证据写进 PROGRESS

最低证据集：`--status` 快照 → 杀掉一个子进程 → 记录端口恢复耗时 → `MainWindowHandle=0` → 项目自身功能回归（模型/接口/页面）→ 日志尾部。
把这些数字写进项目 `PROGRESS.md`，下一次接手的人（或未来的你）才能判断"这管理器到底靠不靠谱"。

## 13. 每个项目一个 exe 时，身份必须唯一（否则两个管理器会互相打死）

形态定为"一个项目一个管理器"后，以下六项**每个项目都要不同**，否则会出现抢互斥体、抢计划任务、互相覆盖状态文件的诡异现象：

| 项 | 当前 codex-router 的值（示例） | 新项目要改成 |
|---|---|---|
| exe 名 | `CodexRouterManager.exe` | `<X>Manager.exe` |
| 单实例互斥体 | `Global\CodexRouterManagerSingleton` | `Global\<X>ManagerSingleton` |
| 计划任务名 | `CodexRouterManager` | `<X>Manager` |
| 状态文件 | `local\.runtime\manager-status.json` | 本项目运行时目录下同类文件 |
| 日志文件 | `local\logs\manager.log` | 本项目日志目录 |
| 托盘图标 | `icon.png` / `icon.ico` | 换一张能一眼区分的图 |

配套习惯：托盘悬浮提示里写清"管的是哪个项目 + 哪些端口"，这样托盘里并排几个图标时不会认错。
